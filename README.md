# m.o — Make it out the groupchat

A free, organizer-first coordination MVP. Pronounced “em-oh.”

## Product center

The setter is the friend who makes an outing happen. m.o gives that person a shared, current plan and helps other people take responsibility. The initial situations are a group trip with shared accommodation and a Friendsgiving potluck where the host keeps asking who’s bringing what. Demo dates, guests and details are fictional.

## Working scope

- Create, edit and delete a shared trip or get-together (only the host can delete; everything in the plan is removed).
- RSVP with the current participant’s name and optional note.
- Guest list: the host adds names, then prepares each person’s personal link in Send invites. New invitations require a random secret distinct from the public guest ID. A guest can reuse their personal link on another device; choosing an answered name alone cannot recover or take over that spot. The host can replace or revoke the link. Replacement, revocation and 30-day expiry invalidate existing device access as well as the old URL.
- Friends who never open the link: the host records what someone told them by text or in person (their answer, extra guests, dietary needs, staying over) and notes who said they’d bring an item. These are labelled “noted by the host, not confirmed” everywhere. That person sees a one-tap “Is that right?” when they do open the link. The host can copy a personal check-in message for anyone (m.o never sends it), and a host-only “Recent updates” list shows what changed, when, and whether the person did it themselves or the host noted it.
- Personal invites: the host's "Send invites" screen opens the phone's Messages app with a personal message for each guest (their first name and their own link), one at a time or "Send to everyone" in order. Each personal link greets that guest by name with one-tap answers. Phone numbers come from Android contacts, iPhone AutoFill Contact (the "Add one person" name and phone boxes), or pasted lists and stay in the host's browser only; m.o never stores them or sends texts.
- Guest answers: "Can't make it" shows a thank-you ("Make it out next time!") and hides the plan's tasks, address and tabs, with buttons to change the answer. Guests who answered (never hosts) see a "Planning something yourself?" card with Start a plan and Set up my profile; "Not now" hides it on that phone. "Still checking" asks when to check back (Tomorrow, In 3 days, In a week, or a day), saves it on the guest (`check_back`, migration 0011; only the host and that guest see it), offers a calendar reminder with an alert, and shows the host "Will decide by …". m.o never sends the nudge itself.
- Fast tab taps: Home, Plans and You replace the address instead of stacking Back steps, only the newest load updates the screen, and double-tap zoom is off.
- Host link (recovery): the host taps "Get my host link" (overview, then More tools once made) to get a private `/h/<key>` link. Opening it on another device and tapping "Open as host" grants that plan to the receiving browser; its own identity and other plans are kept. Only a hash of the key is stored (`host_key_hash`, migration 0010). Making a new link turns the old one off. Tries are capped at 10 per 10 minutes. Replacing a host link removes other recovered-device grants. Legacy releases that copied owner cookies have the compatibility limit described below.
- Short links: shared plan links are `/p/<code>` and personal invites `/i/<code>`; plan links retain their 22-character record ID; new personal links use an independent 43-character random secret whose SHA-256 hash is stored in D1. They redirect to the full `/?plan=…` address, which still works and still shows the group-chat preview.
- Search in "Where": venues and addresses come from OpenStreetMap (free, no key) through `GET /api/places?q=`, capped at 30 searches a minute per person. Home addresses: when the map knows the street but not the house, the typed house number is added to the street result; addresses starting with a number are also checked with the free US Census address finder (no key). With the optional free Ticketmaster key (`TICKETMASTER_KEY` GitHub secret, set as a Worker secret on deploy), events show first: "UniverSoul Circus Raleigh" tries the whole phrase, then the last words as the city. Picking an event fills in the venue address, date and time, and the name if empty. "near me" asks the phone for its rough location (about 1 km) for that search only; it is never stored. Events not sold through Ticketmaster won't show; search the venue instead.
- Booking links: a plan can keep an Airbnb, Vrbo or hotel link (`booking_url`, migration 0008). Pasting one into "Where" moves it to the booking field. It shows as "Open the Airbnb booking" and, like the address, only to the host and guests with host-approved arrival access who said they are coming or checking. m.o can't read the booking or its address. With no booking yet (any plan), "Need a place to stay?" sits under the booking link box and opens an Airbnb or hotel (Booking.com) search for the Where area and dates in a new tab.
- Multi-day plans: "More than one day? Add an end date" adds an end (`end_date`, migration 0009). Everyone sees "Fri, Dec 4, 6:00 PM – Sun, Dec 6", invite texts use it, and Add to calendar spans the whole stay. The schedule offers a Day picker with every day of the trip plus an optional time ("Any time" when left blank), and groups stops by day.
- End times: a get-together can have an end time ("Add an end time", filled 3 hours after the start; it can also be a later day). Everyone sees "Sun, Nov 29 · 4:00 PM – 7:00 PM", invite texts use it, and Add to calendar ends then. Stored in the same `end_date` field as multi-day plans.
- Fixing the bring list: the host has Edit and Remove under each item (only the host; the server checks). Edit fixes the wording, and whoever is bringing it keeps it. Remove asks first and says who had it. Both show in the host's Recent updates. `npm run journeys:items` checks host and guest.
- Changing a plan: Edit plan changes everything without starting over, including Get-together ↔ Trip (logged as "plan type"; items and who has them stay) and adding new items. Existing items are changed or removed on the Bring list / To-do list tab.
- Plan order: Plans and Home list plans by date (`lib/plan-order.ts`, applied by the API): coming up soonest first, then plans with no date (newest first), then past plans (most recent first). A plan is past once it ends: its end time, or 6 hours after it starts; "made it out" counts as past. Same order for hosts and guests. `npm run journeys:order` checks both.
- Link previews: every shared link shows a picture. A plan with its own cover (photo or Genmoji) uses it (`/api/plan/<id>/cover`, 1000×500); other plans use an m.o illustration (`public/og/gathering.png` or `trip.png`, 1200×630) and the home page uses `public/og/home.png`. Regenerate them with `node scripts/og-images.cjs` while `npm run dev` runs. Previews name the host and plan, never the address. `npm run journeys:previews` checks them.
- Bringing someone (plus-ones): a guest who said they're coming or checking sees "Bringing someone?" under their answer. They type a name and tap "Ask <host>" (and can text the host from their own Messages). The host sees "<guest> asks to bring <name>" at the top of the plan and a "1 request" chip on the plan card, then taps "Yes, <name> can come" or "Not this time". Yes puts them on the guest list "with <guest>" and shares arrival details once they answer. The guest can then send them their own personal link, or the host can send it to the guest to pass on. The link is made once, by whoever goes first; only the host can replace or revoke it. Each guest can bring up to 4 people in total, shared with the extra guests on their answer. Edit plan → "Guests can bring someone without asking me" skips the approval. Requests are visible only to the host and the guest who asked. Migration 0015 adds `guests.with_guest` and `plans.open_plus_ones`; pending and declined requests are guest rows with status `requested` or `declined`, kept off the guest list. `npm run journeys:plusones` checks host, guest, stranger and the new guest.
- One way to bring someone (owner's choice): the answer form no longer has a +1 counter; it points guests to "Bringing someone?", so every plus-one is a real guest with their own invite and their own answer. Extras saved earlier stay as they are (the host can still note a +1 for a friend who texted). Pending plus-ones show in the host's guest list ("WAITING FOR YOUR OK") as well as on the overview. A plus-one's invite text says who asked to bring them, whether the host or the guest sends it, and their invite opens with "Hi Cynthia! Mom is bringing you". Both the host and the guest who asked see the plus-one's answer.
- Genmoji pictures: in "Your picture", a third choice, Genmoji, sits between Draw me and Photo. You tap the box, open the emoji keyboard and pick a Genmoji (iPhone with Apple Intelligence) or any emoji. Safari inserts a Genmoji into the editable box as a picture; m.o places it on a background colour you choose (saved pictures can't stay see-through) and saves it through the same checked photo upload. Letters are ignored with a hint. `npm run journeys:genmoji` checks it, with a simulated Genmoji picture.
- Genmoji invites: iPhone doesn't allow Genmoji in plain text boxes (the invite's "Your own emoji" box), so "Customize your invite" also has a Genmoji box (`components/mo/genmoji-box.tsx`, shared with profile pictures). A Genmoji is drawn like an emoji invite (the chosen colour, lights, one big and two small faded copies), saved through the same checked cover upload (1000×500), and redrawn when the colour changes. An emoji typed there styles the invite like the emoji box. The box watches itself (Safari doesn't always send an input event), handles <picture>/<source> and late-loading pictures, explains a blank-placeholder (U+FFFC) Genmoji, reads pasted pictures, and names what arrived if it can't read it.
- Extra guests: a guest can ask to bring up to four people; they count in the headcount only after the organizer approves.
- Dietary needs and sleepover requests are visible only to the organizer and that guest. The address, arrival and house notes, booking link and itinerary require an in/checking answer plus arrival access. Guests the host added by name get arrival access with their personal link, so they see the address as soon as they answer (owner decision, 2026-11-20); before answering they see "Address shows after you answer". Strangers who answer from the group link still need People → Approve arrival access ("Address needs host approval"). The host can hide it from anyone (Hide arrival details). Guests already on live plans before this change keep their current setting. Door codes have a separate host-only field and must be sent through a separately verified channel; personal links never reveal that field.
- Claim, release, add and complete contributions and responsibilities.
- Prevent other guests from taking over claimed items or editing organizer-only details.
- Release a participant’s claimed items if they decline.
- Persist real plans to Cloudflare D1; demo changes stay temporary.
- Put dates, places or anything else to a group vote. Members vote and suggest options; only the organizer can lock one in, and a locked date or place updates the plan. Votes are suggestions, never commitments.
- Keep a live plan: an organizer-maintained itinerary of timed stops and key HTTPS links.
- Replay: after the plan, people who were in post memories (optional HTTPS photo/album link) and shout-outs; the organizer marks the plan “made it out.” Authors and the organizer can remove posts.
- Profile pictures: choose your own avatar (face colour, including skin tones, hair, hair colour, top, background, glasses, hoops) or upload a photo. Photos are cropped and shrunk on the phone (a few KB), stored in D1, and served from a cached URL; people in plans you join can see them.
- “What’s your mo?” profiles: name, unique handle, a one-line mo, interests and planning style. Shown to people in shared plans. The profile page lists plans you made it out to, places conquered, and private counts of what you hosted and took care of — no scores or rankings.
- Home shows the next plan with one deterministic “thing to sort out” (an unclaimed item, an open vote, or a missing date/place) from saved data; plans have Overview, People and Bring list tabs.
- Plan journey (`lib/journey.ts`, shared by the server and the screens): every plan is **In the chat** (no date yet), **Taking shape** (a date, with things still open), **Locked in** (nothing left) or **Made it out** (only when the host marks it). The stage is worked out on the server from the real saved data, so a guest who can't see the address still sees the right stage; it is never stored, so there is no migration. "Things left to make it out" for the host: add who's coming, pick a date, add the place, close open votes, answer requests to bring someone, hear back from people who haven't replied or are still checking, and items with nobody on them. Silence never counts as an answer. Plan cards show the stage, seats ("the table": filled = coming, yellow = still checking, dashed = no reply, crossed = can't make it) and, for the host only, how many things are left. The plan page shows the stage bar to everyone; the host sees "things left" and the table, and guests who answered see the table. Stage names and their one-line meanings are in `STAGES`, so they can be renamed in one place. The tagline lives in `lib/site.ts` (`TAGLINE`).
- Show missing decisions, the next useful coordination step, and copyable group-chat drafts (status update and a nudge for maybes). These are deterministic templates built from saved plan data, not an in-app AI model. m.o never sends messages.
- Download an ICS calendar entry. This is a one-time calendar export, not continuous calendar sync.
- Save an existing HTTPS invitation URL and link back to it. An m.o plan can be added manually as an Apple Invites Link tile. Apple RSVPs are not automatically synchronized.
- Expose eleven authenticated MCP tools through the Site’s ChatGPT plugin. ChatGPT can structure a user’s supplied conversation, create/read/update plans, add unclaimed items, start organizer votes, record the caller’s own RSVP, votes and commitments, add itinerary stops, and draft a group-chat update from saved data. It must not invent commitments, book anything, or send invitations automatically.

## Access

The owner has approved a public pilot. The Site audience itself is changed in the Sites access controls (not in this repo). Once public, anyone possessing a plan’s UUID link can read that plan and respond as a guest; guest sessions can write their own RSVP, votes, claims and posts. Personal invite credentials grant access to one guest record. Forwarded credentials allow replying as that guest, so the UI explains this risk; door codes stay outside the guest API. Other guests’ RSVP notes, dietary needs and check-back details are private. Basic abuse caps apply: 20 new plans per person per day, 150 guests and 100 items per plan, plus existing caps on votes, stops and memories. Do not publish private demo/test data or reuse preview sessions as production guests.

## Running at $0

m.o is built to need nothing paid:

- **No paid services or keys.** No AI provider, email, SMS, maps, payments or file storage (R2 is off). Group-chat drafts are templates, Maps is a plain link, and avatars and artwork are SVG drawn in code. Fonts load from Google Fonts (free).
- **Bounded database use.** Every per-plan query uses an index (migrations 0003–0005), so a request's cost doesn't grow with the total number of plans. An open plan refreshes every 30 seconds while visible and pauses after 10 minutes without interaction.
- **Abuse ceilings.** 20 new plans per person per day, a site-wide ceiling of 500 new plans per day (override with a `DAILY_NEW_PLANS` environment variable), and per-plan caps on guests (150), items (100), votes, stops and memories. RSVPs and existing plans are never blocked by the site-wide ceiling.
- **CI.** One GitHub Actions job on pushes to `main` and on pull requests, with superseded runs cancelled and a 15-minute timeout. Free for public repositories; private repositories use the account’s included Actions minutes.

- **Usage numbers (owner only).** Each action that succeeds adds one to today's count for its kind, like `POST plans` (a plan made) or `POST plan/rsvp` (an answer) (`usage_counts` table, migration 0019). Reads, refused and failed actions aren't counted. It stores the day, the route shape and a number only: no IDs, names, plan details or cookies, and nothing is sent to an analytics company. There is no public page for it. To see it: Cloudflare dashboard → Storage & Databases → D1 → the m.o database → Console, then run `SELECT day, area, n FROM usage_counts ORDER BY day DESC, n DESC LIMIT 100;`. Useful rows: `POST plans` plans made, `POST plan/guests` guests added, `POST plan/rsvp` and `POST plan/guests/response` answers, `POST plan/tasks/pick` items claimed, `POST plan/guests/invite` personal links made, `POST plan/plus-ones` plus-one requests.
- **Security headers.** Every response sends `X-Content-Type-Options: nosniff`, HSTS and a Permissions-Policy (no camera, microphone or payment; location for m.o only, used by address search). Pages also send a Content-Security-Policy: scripts from m.o only (inline allowed for the app's own start-up data; eval only in local dev), styles and fonts from m.o and Google Fonts, pictures from m.o, `data:` and `blob:`, connections to m.o only, and no framing (`frame-ancestors 'none'`, `X-Frame-Options: DENY`). Address and event searches run on the server, so the page needs no other hosts. Checked by `npm run journeys:previews` (also against a production build).
- **Brand.** Direction A ("Good Company"), chosen 2026-11-20; rules in `docs/brand.md`. The logo is drawn (`components/mo/brand.tsx`): the dot in m.o is a head over a table line, a saved seat. Every colour, text size and corner in `app/globals.css` comes from a token. Home-screen icons and `public/manifest.webmanifest` come from `node scripts/brand-icons.cjs`. The manifest opens m.o in the browser, not full screen, because an iPhone home-screen app keeps separate cookies and a host would lose sight of plans made in Safari.
- **Help page.** `/help` answers the common host and guest questions (invites, who sees the address, editing or deleting a plan, the bring list, host link, plus-ones, changing an answer, cost, texting, Apple Invites, deleting data). The answers are fixed text, not AI, and use the app's real button names. Tapping a question opens its answer, and the page ends with "Still stuck?" and the support email. It's linked from the footer, the Help sheet, the not-found page and the Privacy and Terms pages. Reply templates for emails that still arrive are in `docs/support-replies.md`. Update both when a button name changes.
- **Page not found.** Wrong links get an m.o page (`app/not-found.tsx`) with a 404 status, the night-party art, and "Go to my plans" / "Go to the home page".
- **Error alert.** `.github/workflows/monitor.yml` checks the live site every 30 minutes (free: the repository is public). It fails, and GitHub emails the owner, when the home page doesn't load, the database doesn't answer, or `/api/health` counts errors in the last 35 minutes. When an API request fails, m.o writes down only the time and the route shape, like `POST plan/rsvp` (`errors` table, migration 0014, newest 500 kept). It stores no IDs, names or error text. `/api/health` is public and returns counts and route shapes only. The email comes from GitHub's own Actions notifications (Settings → Notifications → Actions → email for failed workflows); details are in Cloudflare (Workers & Pages → mo → Logs). Run it by hand from the Actions tab ("Check the live site" → Run workflow).

- **Restore.** `docs/restore.md` has the steps for a real restore (Cloudflare Time Travel first, then a backup file). The **Restore drill** workflow (Actions → Restore drill → Run workflow) practises it: it backs up the live database (read only), loads the backup into a new practice database, compares row counts table by table and deletes the practice database. Its report shows counts only. `node scripts/restore-drill.mjs --local` rehearses it on the local dev database. D1 backups list tables alphabetically and fail to load as-is; `scripts/restore-order.mjs` puts plans before their guests and items.

What this repo can’t control: the hosting platform’s own plan and usage limits. Check the Site’s hosting account for its free allowance and set any spending limit there.

Photo uploads are not stored by m.o; replay photos are HTTPS links. ## Personal links and arrival access (how it works)

Migrations `0012_military_squadron_sinister.sql` and `0013_graceful_lake.sql` add guest secrets, per-device grants, arrival approval, the host-only door code and a secret lookup index. Existing migrations are unchanged. Apply both new migrations before deploying this code; the existing deployment workflow already applies pending migrations first. No live migration or deployment was run while preparing this branch.

Existing answered spots keep their original device session until the host issues a new personal link. They cannot be recovered just by name. Legacy unclaimed 22-character invitations may still be claimed once; issuing a new secret link disables that legacy authorization. Hosts should replace old personal links and explicitly approve arrival access before rollout. Arrival approvals default to off for existing records. Existing codes in arrival notes are not automatically extracted: move them to the separate host-only field before approving arrival details.

A link is a bearer credential, not proof of a person's real identity. Up to 20 devices can redeem one link. Replacement revokes the prior device grants and keeps the host's arrival choice for that guest (a revoke turns it off; a new link after a revoke turns it back on for a guest added by name); revoked information already seen cannot be retracted. Host-issued plaintext links are cached only on the host's device; D1 keeps hashes. Opening a link on another host device requires preparing a replacement. The guest secret is moved to a URL fragment on redirect, captured in memory, and removed from the visible page URL; avoid logging full invitation paths in external analytics.

The initial HTML response establishes the HttpOnly visitor cookie before parallel client API requests to avoid first-load identity races. Existing host recovery remains unchanged.

`npm run journeys:access` verifies the complete host/guest/revoked-link flow with independent phone sessions and a synthetic local event. It refuses production URLs. API tests also cover answered-spot takeover, replacement, expiry, cross-guest writes, note privacy, arrival approval and door-code exclusion. Hosted deployment and real-user verification remain outstanding.

## Host recovery and planning fixes (how it works)

Source checked on 2026-11-20: main `e3e760c` includes monitoring and the successful restore drill. PR #25 was inspected at `469371f` and then merged as current main `9d33a2e`. It adds item editing/removal, plan-type changes, end times, empty new bring lists and the phone invitation-layout fix. This branch was rebased onto current main `9d33a2e` and preserves that work. It has not been deployed.

Apply new migration `0015_sudden_ironclad.sql` before deploying this branch. It adds `host_access`; earlier migrations are unchanged. New host recoveries keep the receiving browser identity and grant one plan only. Replacing the host link invalidates other recovered-device grants; the device making the replacement keeps its access. Existing plans and original owner sessions remain valid. Important compatibility limit: browsers recovered under older releases already copied the original owner cookie. They cannot be distinguished from the original owner or retroactively revoked by this migration. If that old credential was compromised, use a fresh browser identity and recreate the affected plan; do not assume link replacement removed a legacy copied cookie.

Guest links are redeemed before their secret is removed from the URL. Redemption restores a scoped record; it does not RSVP or confirm anything for the guest. Refresh then remains usable. Status-only RSVP changes preserve saved notes, dietary details, overnight requests and plus-ones; explicitly supplied form fields can still clear them. Cross-device contribution totals include currently authorized scoped grants. A global profile remains owned by its browser; personal links never silently grant a global profile or unrelated plans.

Finalizing a date vote validates the existing end date first. If the result would be invalid, the host must edit the trip end before finalizing. ### Verified integration identity

The public Workers host cannot trust an arbitrary `oai-authenticated-user-id` header. Browser access uses its HttpOnly visitor cookie. API/MCP integration identity is accepted only when a trusted gateway signs the request with a separately configured `MO_IDENTITY_SECRET` Worker secret. No production secret or gateway was configured by this branch. Until the gateway is configured, identity-dependent ChatGPT tool calls fail closed with a browser fallback message; discovery remains available. This is an integration setup requirement, not a guest-browser sign-in requirement.

Gateway identities must not be UUID-shaped browser bearer IDs. Prefix UUID-based user IDs in the gateway (for example `gateway:<user-id>`); the verifier rejects IDs shaped like browser cookies to keep the two identity domains separate. Gateway contract: generate a random secret of at least 32 bytes; keep it only in the gateway and Worker secret store. Send `oai-authenticated-user-id`, `x-mo-identity-time` (Unix seconds), and `x-mo-identity-signature` (lowercase hex HMAC-SHA256). Sign the UTF-8 string formed by joining timestamp, HTTP method, URL path plus query, actor ID, and lowercase hex SHA-256 of the exact request body with newline characters. Assertions are valid within five minutes of Worker time. Body, method, path/query, identity and timestamp are bound to the signature. TLS is still required. Internal MCP-to-API calls preserve the verified identity without forwarding a public header.
